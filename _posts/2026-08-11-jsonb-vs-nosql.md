## 들어가며
프로젝트를 진행하며 구조가 일정하지 않은 가변적인 데이터를 저장해야 하는 상황이 있었습니다. 이러한 데이터를 어떤 방식으로 저장하고 관리하는 것이 적절할지가 고민이었고, RDB의 jsonb 타입과 NoSQL을 비교하며 각각의 특징과 선택 기준을 정리하려고 합니다.

## 1. RDB의 jsonb와 NoSQL
### 1-1. 데이터 구조의 유연성
jsonb 타입과 NoSQL 모두 가변적인 데이터를 저장할 수 있습니다. 따라서 단순히 데이터 구조가 자주 바뀐다는 이유로 NoSQL을 사용하자고 판단하기에는 근거가 부족합니다.
### 1-2. 관계형 연산의 필요 여부
jsonb 타입은 RDB 안에서 사용되기 때문에 다른 테이블과의 JOIN, 트랜잭션, 제약 조건 등 관계형 DB의 장점을 함께 활용할 수 있습니다. 하지만 NoSQL은 데이터 간의 관계가 적고 독립적인 데이터를 저장하고 조회하는 데에 적합합니다.
### 1-3. 데이터의 생명주기
일정 기간 후 삭제되어야 하는 데이터라면 주기적인 삭제 요청보다는 TTL을 이용하여 관리하면 좋습니다. RDB의 경우는 스케줄러를 통해 만료 데이터를 삭제하는 방식으로 구성해야 하지만 NoSQL은 TTL을 사용하여 요청 없이 만료되게 할 수 있습니다. 
DynamoDB 에서는 TTL이 만료가 되면 백그라운드 프로세스가 식별하고 삭제합니다. 하지만 만료되자마자 삭제하는 것은 아닙니다. 공식 문서에 따르면 만료되고 며칠 이내에 삭제가 되며 처리량을 소모하지 않는다고 되어있습니다.
### 1-4. 확장성과 운영
DynamoDB는 데이터를 파티셔닝하는 방식으로 수평 확장을 지원합니다. 따라서 사용자가 직접 샤딩을 할 필요가 없습니다.

## 2. 왜 NoSQL인가?
### 2-1. 다른 데이터와 관계가 적은 독립적인 데이터
저장하려는 데이터가 다른 데이터와 관계가 크지 않았습니다. 해당 데이터를 조회할 때 다른 테이블과 join이 필요 없었습니다. 
### 2-2. 일정 기간 후 삭제되어야 하는 데이터
데이터의 생명주기가 명확했습니다. 해당 데이터는 영구적으로 보관되는 데이터가 아니라 일정 기간이 지나면 삭제되어야 했습니다. 그렇기에 별도의 삭제 로직과 실패 처리는 또 하나의 비용이었습니다. 반면에 DynamoDB는 TTL을 통해 각 데이터의 만료 시점을 지정할 수 있어 데이터 생명주기 관리를 단순화할 수 있었습니다.
### 2-3. 데이터 증가에 따른 확장성
DynamoDB는 데이터를 파티션에 분산하는 방식으로 수평 확장을 지원합니다. 파티션 관리와 샤딩을 직접 수행할 필요가 없기에 관리 비용을 줄일 수 있었습니다. 현재 규모에서 필요한 기능은 아니지만 데이터와 요청량이 증가했을 때 직접 샤딩을 하지 않아도 된다는 점이 장점이었습니다.
### 2-4. 정리
결국 DynamoDB를 선택한 이유는 단순히 스키마가 유연하기 때문이 아닙니다. 데이터 간의 관계가 적고, 생명주기가 명확하며, 관리 비용이 적기 때문입니다.

## 마치며
가변적인 데이터를 다뤄야 하기 때문에 반드시 NoSQL을 선택해야 하는 것은 아닙니다. RDB에서도 jsonb 타입을 활용하면 가변적인 데이터를 저장할 수 있으며, json 으로 저장하고 Java 객체로 받아올 수 있어 유용합니다. 

이번에 중요하게 생각한 것은 단순히 데이터의 형태가 아니었습니다. 데이터 간의 관계와 어떤 방식으로 조회되는지, 얼마나 오래 보관되는지, 그리고 운영하기 위해서 어떠한 비용이 필요한지였습니다. 이러한 특성을 고려했을 때 제가 다루는 데이터에는 NoSQL이 더 적합하다고 판단하였습니다.

데이터베이스를 선택할 때는 특정 기술의 장점만 보고 결정하기보다는 데이터의 특성과 사용 패턴을 먼저 파악하고 그에 맞는 방식을 선택하는 것이 중요하다는 것을 생각할 수 있었습니다.
